# Zerg 0.1.0 — release notes

The first release, and therefore the first entry with nothing to compare itself against: everything below is
new, and what these sections are really doing is saying what exists and — as carefully — what does not.

The short version is [`CHANGELOG.md`](../../CHANGELOG.md) at the repository root. This is the long one.

## How to read this

**Which compiler.** `make` builds two. `zerg0` is a Go-hosted seed whose only job is building the compiler;
`zerg` is that compiler, written in Zerg, and the one a build puts in `bin/`. **Every claim below is about
`zerg`.** The seed's narrower subset is its own contract, in
[`src/bootstrap/README.md`](../../src/bootstrap/README.md), and a reader writing Zerg never meets it.

**The standing contract.** A form is either lowered correctly or refused **by name** at compile time. Never a
crash, never a silently wrong answer, and never an error reported by `cc` or the linker against generated code
nobody wrote. That is why the limitations below can be a list rather than a warning: each one is a sentence
the compiler will say to you, and most of them quote the code it says it with.

**The markers.** The specification states the intended language and marks each gap in the chapter it belongs
to — `[not yet]` for a form that is specified and refused by name, `[deviation]` for a behaviour that does not
match and is a bug with a fix owed, `[implementation-defined]` for what the spec declines to pin. Silence
means it works. The vocabulary is [Conformance](../../docs/conformance.md).

**Why this document does not list them.** It used to. Eighteen deviations were written out here in full
prose, and sixteen days later **the five it led with were all false** — every one had been fixed and the
paragraph had not moved. A release note is frozen by design and the compiler is not, so a second copy of a
moving list is a copy that lies with a version number attached. What follows instead is the **shape**: how
many, of what kind, and which ones a careful reader still cannot discover on their own. The list itself
lives with the markers, and every one of the 173 was re-measured against this commit.

## What ships

**One binary and two trees.** `bin/zerg` is not self-contained: a build ends in `cc`, and the compiler reads
the runtime's C sources and the standard library at run time. A released artifact is therefore a per-platform
tarball laid out the way `make install` lays out a prefix, and **`cc` is a dependency of the installed
compiler**, not only of building it.

|                      |                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------ |
| **Platforms**        | `linux-x86_64`, `linux-arm64`, `macos-arm64`                                         |
| **Intel Mac**        | no binary — build from source. Rosetta runs x86_64 on Apple Silicon, not the reverse |
| **Commands**         | `build` `test` `fmt` `lint` `desugar` `doc` `lsp`                                    |
| **Standard library** | 15 modules, ~7.4k lines, pure Zerg over a syscall floor                              |
| **The compiler**     | ~39k lines of Zerg, compiled by itself; `make fixpoint` proves it                    |

**The standard library.** `ascii` `cli` `fs` `io` `json` `log` `math` `os` `rand` `sha256` `strconv`
`strings` `testing` `time`, and `atomic` — which ships and cannot be imported, because it declares a generic
`struct` and this compiler has none. That one is named where it is reached rather than left to fail.

**Documentation.** A normative specification in twelve chapters, in English and Traditional Chinese, held
pairwise by a gate. [Getting started](../../docs/getting-started.md) takes `hello, world` to a program in
more than one file; [Zerg by example](../../examples/README.md) is 33 programs in a reading order, each one
built and run by a gate.

## Known limitations — 139 forms, specified and refused by name

The specification is deliberately larger than this compiler. Every gap is marked in its chapter and every
one is a clean refusal, most of them quoting their own code — `E9056 NotImplemented: the list method
`map``, `E9038`, `E9029`, `E9010`, and so on for fifty more. Naming one is how you find out.

The families, so a reader knows what to expect before writing the program:

- **Generics beyond a free function.** A generic `fn` is built. A generic `struct`, `enum` or **method** is
  not, and neither is an `impl` whose target carries type arguments.
- **Specs as types.** A `spec` is a bound, not a type: a spec-typed parameter is refused. Of the built-in
  specs the prelude promises, `Eq` and `Into[T]` exist; `Ord`, `Hash`, `Error`, `Iterator`/`Iterable` and
  every operator spec are not declared at all, so naming one is the ordinary "no spec named" message.
- **Containers.** `list[T]` and `map[K, V]` are built. `set[T]`, the fixed-size array `[T; N]`, the checked
  `get`, `slice`, `insert`/`remove`, the adapters `map`/`filter`/`fold`/`retain`, and `==` between two
  containers are each refused by name.
- **Patterns.** Destructuring at a `:=`, a list, tuple, struct or `as` pattern in a `match`, and a
  sub-pattern inside a variant payload.
- **Text and formatting.** The f-string `!r`/`!s`/`!a` conversions, the `:spec` format spec, and the
  self-documenting `{x=}`. A composite in a hole is refused rather than rendered.
- **The fixed-width ladder.** `i8`…`i64`, `u8`…`u64`, `f32`, `f64` — none of it, in any position.
- **Streams and processes.** `io.read_file` / `io.write_file` are the pair that is wired; the `File` handle,
  `open`/`create`, and the `stdin`/`stdout`/`stderr` stream objects are not. Command literals are lexed and
  then refused by name.
- **The package layer.** There is no manifest, no version, no resolver and no dependency fetch. A build is
  an entry file and the modules its imports reach, from three roots: the standard library by a bare name,
  this project by `./`, and a remote path reserved and refused by name.
- **FFI.** Neither edge is built; that chapter is a design.

## Known deviations — 34, and what kind each is

A deviation is a behaviour that does not match the specification: **a bug with a fix owed, not a documented
state.** They are grouped here by _how_ they fail, because that is what decides whether a reader can protect
themselves.

### Silent — the program compiles and nothing says a word

These are the ones a careful reader cannot discover, and there are three:

- **Evaluation order is unspecified in two forms.** An enum variant's payload — `E.V(f(1), g(2))` — and a
  call through a **function value** hand their operands to one C construct and inherit C's order, where the
  specification says left to right. It takes two effectful operands to observe at all, and everything else
  in the language is ordered.
- **A coroutine that never runs leaks its environment.** The captures are filled at the `spawn` and released
  by the body, so a `spawn` the scheduler never reaches — a program that ends first — leaks a reference per
  captured value.
- **A body inside a template nobody instantiates is never checked.** Only the specializations a call asks
  for are lowered, so `fn f[T](xs: list[T], v: T) { xs.append(v) }` that no call reaches compiles in
  silence, and so does the same body writing to an immutable binding. The seed diagnoses both.

**The five this document led with in its previous draft are all fixed** — a `str` literal `match` arm now
fires, an if-expression checks that its branches agree, `~` on a `byte` answers at byte width, a `Right`
returned from `main` prints and exits non-zero, and a module-level inferred binding builds.

### A refusal the specification promises that does not arrive

**The iteration freeze sees only a bare name.** `for x in xs { xs.append(x) }` is a compile error; the same
structural change reached through a path — `for x in p.xs { p.xs.append(v) }` — is not. The loop walks a
copy-on-write snapshot, so the program stays memory-safe and the answer is well defined; what is missing is
the diagnostic this section promises.

### A crash where a diagnostic is owed

- **Freeing a long chain** recurses one C stack frame per node.
- **A stack overflow** is the operating system's fault report, not a Zerg abort — the runtime does not own
  or depth-check the stack.

### A diagnostic that is not up to the contract

- **The f-string scanner's two raises carry neither a code nor a place**: an unterminated `f"abc` and a bare
  `}` inside an f-string answer with a bare sentence. Every other refusal in the compiler goes through a
  channel that takes the code and reads the place itself.
- **`zerg desugar --check` is right about the exit status and wrong about the reason.** It compares the file
  against canonical-formatted core, so a file with no sugar in it fails on whitespace, saying _still holds
  sugar_.
- **`zerg fmt --check` certifies a file `zerg build` refuses.** A group the pass declines keeps its trailing
  comma; `fmt --check` exits 0 and the build reports `E2046`.

### The layer that is not there yet

The remaining deviations are one absence seen from several sides: there is no package, so the privacy unit
is the module rather than the package, symbol names carry no package segment, and `init()` runs eagerly
before `main` rather than lazily at first use. They are marked where each is met.

## What this release does not promise

**There is no compatibility promise.** 0.1.0 is the first number, not a stability claim: the surface will
move, and a `[not yet]` becoming built is the ordinary way it will move.

What **is** promised is the standing contract — a form is implemented or refused by name — and that the
specification says which is which, in the chapter where you meet it.
