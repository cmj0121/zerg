# Zerg 格式化器與檢查器規則

`zerg fmt` 與 `zerg lint` 套用的每一條規則，以及指名它的代碼。屬於
[語言參考](../language.zh-TW.md)的一部分。亦有 [English](fmt.md)。

每條規則都有**代碼**，讓它可以被指名——在診斷裡、在 review 裡、在把它關掉的命令列上。前綴用來
分組，做法與 Python 的 linter 相同；分組的依據是**規則做什麼**，而不是哪一個 pass 實作它。

| 前綴   | 分組        | 是什麼                                       |
| ------ | ----------- | -------------------------------------------- |
| `F1xx` | 版面        | 在哪裡斷行、縮排多深                         |
| `F2xx` | 間距        | 兩個 token 之間放不放空白                    |
| `F3xx` | trivia      | 人為了人而寫下的東西會發生什麼事             |
| `F4xx` | 改寫        | 會**移動**程式碼、而不只是排版的規則         |
| `L1xx` | 死碼        | 寫下來但沒有任何東西到得了的東西             |
| `L2xx` | null safety | 一個 optional 運算子做的事和它看起來說的不同 |
| `L3xx` | 捕獲        | coroutine 與延後呼叫實際拿到了什麼           |
| `L4xx` | 解析        | 一個名字對應到不只一個東西                   |
| `L5xx` | 轉換        | 字面值取了紙面上看不出來的型別               |
| `E1xx` | 詞法        | 不構成 token 的文字                          |
| `E6xx` | 剖析        | `E2xx` 用完之後,不構成 Zerg 形式的 token     |

## `zerg fmt`

```sh
zerg fmt <file.zg>...              # 就地重寫；印出它改動過的檔案
zerg fmt --check <file.zg>...      # 報出哪些不是標準形式，不改動任何東西
zerg fmt --off F401 <file.zg>...   # 放過某一條規則（可重複）
```

格式化器從 **token** 出發，不從 AST。這正是整個設計決定：AST 已經丟掉了讀者放進去的註解與空行，
而一個會吃掉這些東西的格式化器，沒有人會跑第二次。

它**依構造而冪等**——輸出由「輸入本身會產生的同一串 token」建出，所以對已格式化的原始碼再格式化
不會有任何改變。

`--check` 就是 CI 會問的那個問題——這棵樹是不是已經是標準形式——而且不碰任何東西就回答，不是的話
以非零結束。它存在的理由是：問這個問題的 gate 原本是用 shell 寫的（複製每個檔案、格式化副本、`cmp`）。
一個無法被詢問的格式化器，每個 CI 都會重新發明一次。

**它不會重寫括號沒有閉合的檔案。** 讀 token 意味著只要能 lex 它就會重排，於是一個有語法錯誤的檔案
會被重排並以 0 結束——token 完好，但間距是由一組沒有任何真實依據的規則決定的。這道關卡是括號平衡而
不是 parse，這是刻意的：格式化器必須能處理編譯器**編不了**的原始碼，那正是有人會需要它的時候。
一個括號平衡但仍然格式不良的檔案，跟以前一樣會被格式化。

### F1xx — 版面

| 代碼   | 規則                                        |
| ------ | ------------------------------------------- |
| `F101` | 每層縮排一個 tab；`}` 收在它展開時的那一層  |
| `F102` | 一行一個敘述——lexer 插入的 `;` **就是**斷行 |
| `F103` | 換行的運算式，每多一層括號就多縮排一層      |
| `F104` | 連續空行只留一行，群組內也是                |
| `F105` | 跨行的括號群組，收尾自成一行                |
| `F106` | 一段連續的 arm，每個 `=>` 都落在同一欄      |
| `F107` | 一段連續的行尾註解，每個 `#` 都落在同一欄   |

`F105` 就是讓換行的鏈式有一個看得見的結尾：

```zerg
a := (
 builder()
 .run()
 .fast()
)
```

而不是一個要讀者去數的 `))`。它適用於任何「收尾比展開晚一行」的 `(` 或 `[`，所以換行的引數列表
也會得到同樣的形狀。

`F103` 數的是括號而不是敘述，所以巢狀的群組每多一層括號就多縮一層，每個收尾都落在自己的開頭底下：

```zerg
x := sum(
 sum(
  1,
  2
 ),
 3
)
```

改以敘述為基準的話，一個巢狀裡的每個收尾都會擠在同一欄，讀者分不出誰關誰——而且內層的收尾會跑到
它所關內容的**左邊**。

多行鏈式外面的括號不是裝飾，是**它能被解析的原因**：`)` 之後的斷行會結束該敘述（見
[`GRAMMAR`](../../GRAMMAR) 的 ASI 規則），而未關閉的 `(` 內不會插入 `;`，所以括號正是把整條鏈綁在一起的東西。

`F106` 把「對一個小的封閉集合做 match」讀成它本來的樣子——一張**查表**——並把它的 arm 排成一列列：

```zerg
Tok.Eof       => "EOF"
Tok.Illegal   => "ILLEGAL"
Tok.FStrBegin => "FSTR_BEGIN"
```

而不是一道參差的左緣、答案散落在後面。`F107` 是同一個 pass 換一個對齊標記而已，因為「一欄註解貼著
一欄程式碼」是用同樣的方式讀的：

```zerg
kind: int   # what the lexer decided this is
lexeme: str # the source spelling, kept verbatim
line: int   # 1-based, for a diagnostic
```

一個 **run** 是連續、同一縮排層、且每行都帶有該標記的那些行。其他任何東西都會終止它，而這些邊界
才是規則的主體：

- 空行，或自成一行的註解——後面接的是新的一段，而一段會帶自己的欄位；
- 帶 **guard** 的 arm——`n if n > 99 =>` 是一個句子而不是一列，所以它不跟任何東西對齊，並終止它遇到
  的那個 run；
- body 是 **block** 的 arm，或把 body 放到下一行的 arm；
- head 比該 run 最窄的那個寬超過 **12 欄**。

最後一條是預算，它限制了任何單一行會吃到的 padding：沒有它，一個 run 會一個 arm 一個 arm 地愈長愈
寬，最後一個三個字元的 pattern 離它的答案有半行遠。12 是以 `select` 量出來的——它的 arm head 有四
種不同形狀：`v := <-work`、`<-quit`、`out <- total`、`_`，而 8 會把 `_` 那一行切出自己的表。

padding 用**空白**、縮排仍然是 **tab**，所以這一欄在任何 tab width 下都成立：run 內的 tab 完全相同，
會互相抵消。一行可能因此超出 `F403` 換行的欄位，最多超出一個預算的量——這是換來一張表的代價。

標記來自 printer，而不是來自對成品文字的掃描，這一點是承重的而非細節：token 一旦丟掉，字串常值裡的
`=>` 和一個 arm 的 `=>` 讀起來完全一樣，而去 pad 那一個並不會排出一張表——它會改寫那個字串。

Idempotence 仍然是 printer 的。兩個 token 之間的空白不是 token，所以第二次 pass 把補過 padding 的
原始碼 lex 成同一串 token、印出同樣的一個空白、再把它 pad 回同一欄——這也是 `F201` 寫成「至少一個
空白」的原因。

### F2xx — 間距

| 代碼   | 規則                                                          |
| ------ | ------------------------------------------------------------- |
| `F201` | 二元運算子兩側、逗號之後各一個空白；`=>` 兩側至少一個空白     |
| `F202` | `(` `[` 之後、`)` `]` `,` 之前、名稱與它的 `(` 之間，都不空白 |
| `F203` | 前綴運算子緊貼它的運算元——`-1`、`&x`、`<-ch`                  |
| `F204` | range 運算子緊貼它的兩個邊界——`0..n`、`a..=b`                 |

`F203` 由**左邊**決定，而不是由「它是哪個 token」決定。`-` 同時是負號與減號、`<-` 同時是接收、
送出與方向標記；每一個都只在「它前面沒有任何可當運算元的東西」時才是前綴。判斷反了會重印成一個
**穩定的**錯誤形式——`-1` 變成 `- 1`，第二次重印還是一樣——所以 idempotence 檢查看不到它，只有真的
含有該形狀的案例才抓得到。

`F204` 是同一課再上一次。range 運算子是二元的，所以預設說「要空白」，於是 `xs[1..3]` 被印回
`xs[1 .. 3]`——但一個 range 讀起來是**建構子**而不是一次運算，而這棵樹、`GRAMMAR`、以及這些文件裡的
每一個 range 都寫成緊貼的。它活這麼久，是因為 fmt 語料庫裡根本沒有任何一個 range。

兩個例外，都是真的：逗號欠的那個空白留著，所以 list pattern 的 rest 標記是 `[h, ..t]`；以及「不可能
開始一個邊界」的 token 前面那個空白也留著，因為 `20.. =>` 印成緊貼是 `20..=>`——它會被 lex 成 `20`、
`..=`、`>`。formatter 本來會把一個能跑的 arm 改寫成一個 parse error。

| `F301` | 註解保留原文，自成一行或跟在它原本跟隨的程式碼之後 |

### 註解裡的範例

註解裡的程式碼範例以 **doctest 提示符**標記——`>>>` 起一個頂層項目，`...` 接續它：

```zerg
# Example — greeting someone:
#
# >>> fn main() {
# ...     print greet("world")
# ... }
#
# and it prints:
#
#     hello, world
```

`F301` 原封不動保留這一切；提示符是慣例，格式化器不從中讀出任何意義。哪一行用哪個提示符同樣
是撰寫慣例——兩者都表示「這一行接下來是 Zerg」。

標記是**明確的**，而這是關鍵決定。註解裡有兩種縮排區塊：原始碼，以及程式**印出來**的樣本。
單靠版面推斷會把後者當成前者染色——在 `cli` 自己的檔頭，一段貼上的 help 畫面會讓 `Options:`
變成欄位名、`--output` 變成運算子、`VALUE` 變成型別。錯的高亮比沒有高亮更糟，所以由作者說明
哪個是哪個。

用提示符而不是 `圍欄，是因為註解將來要產生文件，而那個產生器輸出的是 markdown——
也就是說` 是**輸出**的語法。把輸入也拼成同一個樣子，會讓「必須把一種原樣傳遞、同時產生
另一種」的產生器，光看形狀分辨不出兩者。

### F4xx — 改寫

| 代碼   | 規則                                                          | 預設 |
| ------ | ------------------------------------------------------------- | ---- |
| `F401` | 只含一個跳轉的 if 區塊，收成它本來就是的後綴 guard            | 啟用 |
| `F402` | import 分組——標準函式庫在前、其餘在後，各組字母序             | 啟用 |
| `F403` | 引數列表要嘛一行，要嘛一個元素一行——不會各半                  | 啟用 |
| `F404` | 兩個以上的 import 收成一個括號 group                          | 啟用 |
| `F405` | 用 `+` 拼出來的字串，收成它本來就是的 f-string                | 啟用 |
| `F406` | 在必要處加空行：guard 段、宣告段、引導區塊的註解              | 啟用 |
| `F407` | 丟棄用的 receive binder 直接刪——`_ := <-ch =>` 就是 `<-ch =>` | 啟用 |
| `F408` | 連續整數的 or-pattern 收成它本來就是的 range                  | 啟用 |
| `F409` | 以 binding 開頭的裸 block,收成它本來就是的 `with`             | 啟用 |

`GRAMMAR` 把 `return x if c`、`break if c`、`continue if c` 與 `raise e if c` **定義為** `if c { … }`
包住同一個跳轉的糖——一個後綴 `if`，涵蓋每一種 **diverge**。兩種寫法說的是同一件事，而其中一個用四行說。格式化器選短的
那個——那正是 guard clause 的用途：例外的出口不再打斷它所守護的那段程式的形狀。裸的提早返回也
一樣：`return if c`。

「優先使用糖」是這裡的通則，不是為 `return` 開的特例：**只要語言為「已經寫下的東西」提供了更短
的表面形式，標準形就是短的那個**，讀者也就不必再去注意兩者是同一件事。

把這條規則反過來讀的是 [`D101`](desugar.zh-TW.md)，兩者互為對方的測試：一份 source 走過兩者會回到自己。
其餘的論證在 `zerg desugar` 那邊——sugar 形式與 core 形式必須建出同一個程式，而 `make desugar` 就是去問
這件事的那道 gate。

**已經帶著自己 guard 的跳轉**會留在它的區塊裡。沒有任何單一的 `if` 說得出 `if m { return 0 if n < 0 }`
所說的事,而寫成 `return 0 if n < 0 if m` 會是任何編譯器都無法解析的原始碼——所以這條規則選擇放手,
而不是自己發明一個。

要注意這個後綴 `if` **不是**什麼：它掛在跳轉上，不掛在運算式上——Zerg 沒有 `A if X else B`。
條件**運算式**是區塊形式，而且 `else` 是強制的：`x := if c { 1 } else { 2 }`。

```zerg
fn clamp(n: int) -> int {          fn clamp(n: int) -> int {
 if n < 0 {                             return 0 if n < 0
  return 0                   →       return 9 if n > 9
 }
 if n > 9 {                             return n
  return 9                       }
 }
 return n
}
```

它只改寫**不會弄丟任何東西**的情況，其餘一律不動：

- 區塊內恰好一個敘述，而且是跳轉；
- 沒有 `else`——else 帶著第二個分支，guard 形式承載不了；
- 內部任何地方都沒有註解，因為註解是人放進去的，而這個 pass 沒有地方把它放回去。

`F402` 是 Go 的慣例，理由也相同：import 清單被**讀**的次數遠多於被改，而分組且排序過的清單，
讓「這個檔案有沒有用到 X」用看的就知道，不必逐行掃。標準函式庫排在前面，因為那是讀者已經
知道的部分；其餘則是這個程式自己帶進來的。

什麼算標準函式庫，是那組固定的隨附模組。模組以路徑的**最後一段**解析，所以 `import "std/io"`
會和 `import "io"` 分在同一組。

它只改寫一連串單純的 `import "path"`，一旦其中出現別的東西就放棄——註解（它屬於它所在的那個
import，排序會讓它變成孤兒），或 `import pub`（它的 re-export 是作者選定的順序）。

接著 `F404` 把這串收進 `GRAMMAR` 給 `import` 的括號形式，一行一個 spec，而 `F402` 的那個空行
會活著進去，在裡面當同樣的分隔：

```zerg
import "cli"          import (
import "zerg"    →        "cli"
import "io"               "io"

                          "zerg"
                      )
```

那裡的排序是 `F402` 的，括號是 `F404` 的。兩者一起呈現，因為那才是 `zerg fmt` 印出來的東西——
中間那個狀態沒有人看得到。

**只有一個 import 就不動它。** 這是 gofmt 的答案，理由也是 gofmt 的：group 的用途是把一份清單
綁在一起，而只有一個元素的清單，就是那個敘述本身加上兩行儀式。

和 `F402` 不同，`F404` 會把 `pub` 與 `as` 一起收進去——那兩者正是 `F402` 放棄的原因，因為
`F402` 會**重新排序**，而這條規則不把任何東西移到別的東西前面：

```zerg
import (
 "io"
 pub "util/text"
 "a/text" as at
)
```

只要 import 之間有註解就放棄，理由同 `F401`；已經是 group 的那一串則原封不動。而在整串**之後**
的註解屬於下一個宣告，所以它只是讓這一串結束，不會讓規則放棄。

寫得出這個形式，也正好找出 self-hosted parser 讀不回它：group 被吃掉、一個路徑都沒回傳，於是
一個用 group 匯入的檔案交給 driver 的是**空的** import 清單——而失敗會在好幾個階段之後，以一個
未知的型別名冒出來，不是在那個沒被讀到的 import 上。

`F105` 說的是「群組已經跨行之後，收尾該放哪」；`F403` 說的是「已經跨行的群組長什麼樣」。
**作者放得下一行的，就留在一行**——這條規則從不去拆一個原本沒被拆開的群組。

作者**確實**拆開過的群組，會被併回一行，除非以下任一條否決：

- 攤平成一行後，它會結束在第 80 欄或更後面——一個 tab 算 4 欄；
- 它有 6 個或更多頂層元素。

只要有一條否決，群組就改為在**每一個**頂層逗號斷開。不會各半：一個只圍著其中一個元素斷行的
群組，以前會把其餘的印在收尾後面，留下一條掛在尾巴上的 `), 3`，那兩種形狀都不是。

```zerg
x := sum(                        # 之前
 1,
 2,
)
y := sum(sum(
 1,
 2,
), 3)

x := sum(1, 2)                   # 之後
y := sum(sum(1, 2), 3)
```

寬度才是真正的判準，而數量是給寬度看不見的情況留的保險：六個引數不論多短，都是一份要用掃的
清單，而不是一行要用讀的程式。

> **[deviation]** 被這個 pass **放過**的群組會留著它的尾逗號,而之後也沒有別人反對。`x := sum( # before`
> 底下接著 `1,` / `2,` 時,開頭那行帶著註解,於是 `F403` 讓群組保持斷開——而 `zerg fmt --check` 會說這個檔案
> 是 canonical、exit 0,`zerg build` 卻用 _E289 a trailing comma before the closing `)` of an argument list_
> 拒絕同一個檔案。一個為編譯器不收的檔案背書的 formatter,比一個把它重排掉的還糟,因為那張背書就是它的全部意義。

兩條門檻都**不會下令**斷行，這是刻意的。這個 pass 一次只看到一個群組，而不是整行，所以跨過第
80 欄的是那行**最後**一個群組，而不是值得斷開的那個——在 `return 0 if a or b or c(x, y)` 裡
那是 `c`，它的兩個引數會被攤成三行，而真正讓這行變長、又沒有括號可斷的那個條件，卻原封不動。

有一件事**確實會**下令斷行：**內含 block** 的群組。`f(match n { … })` 沒有一行的形式可選——block 的 `{`
會結束它那一行，那是印表器的規則、不是這條規則的——所以把它當一行來量，產生的形狀既不是併起來也不是拆開，
還把 closer 留給 `F105` 在**下一次**執行時才搬。這讓 `zerg fmt` 在這棵樹裡沒人寫的那種輸入上失去 idempotent：
call 裡面放一個 block。內含 block 的群組不管作者怎麼寫都算跨行，並且在每個頂層逗號處斷開。

**作者寫在一行上的 `guard` block 不算其中之一。** `guard { e } ?? d` 是行內的一個運算式，而
`check("max + 1 raises", guard { max + 1 } ?? 7, 7)` 讀起來就是它本來的那一行——攤開要七行，而光一個範例裡
就有十八個。所以印表器的 block 規則不套用在它身上：`{` 後不斷行、`}` 不自成一行、中間不進一層，外面那個群組
也就像其他群組一樣被量。這個豁免是**逐個 guard 掙來的**，不是給關鍵字的——到 `}` 為止的每個 token 都必須待在
作者的那一行上，且不得是註解（它會吃掉整行剩下的部分）或 `;`（第二個 statement 就又是一個 block 了）。作者
自己斷開的 guard 保留 block 形狀、連斷行一起保留：這條規則永遠不**併行**，它只是不去斷行。

**沒有頂層逗號**的群組兩條門檻都豁免。鏈式與括號包住的運算式，斷在它們的作者斷的地方——那些斷行說
的是「步驟在哪裡」，而不是「這行放不下了」。它們得到的是「開頭自成一行」，於是每個步驟都從
同一欄開始：

```zerg
n := (
 builder()
 .run()
)
```

和 `F401` 一樣，只要內部任何地方有註解就整組放棄：註解是人放進去的，而把行併起來沒有地方把它
放回去。

**尾隨逗號一律拿掉**，併行或斷行都一樣，而且這是修好而不是偏好：`GRAMMAR` 把逗號寫在元素**之
間**，任何地方都不推導出收尾括號前的那一個——呼叫沒有、tuple/list/map 字面值沒有、簽名也沒有
——所以帶著它的檔案根本不是 Zerg 程式，編譯器會這樣說（`E289`）。格式化器讀的是 token 串而不是
語法樹，這正是它能修好一個 parser 會拒絕的檔案的原因——而那正是人會去找格式化器的時候。

`F405` 是 `F401` 的原則套用在字串上：只要語言為「已經寫下的東西」提供了更短的表面形式，標準形
就是短的那個。

```zerg
"n=" + s + " of " + t                    →   f"n={s} of {t}"
"v=" + strconv.to_string(n, 10) + "!"    →   f"v={n}!"
```

格式化器沒有型別，而這裡也不需要。`+` 從來不是異質的——emitter 只在左運算元是 `str` 時才把它降到
字串串接——所以**一條鏈裡任何一個字串字面值，就決定了整條鏈的型別**。那就是觸發條件。

`strconv.to_string(X, 10)` 收成 `{X}`，因為 base 10 本來就是 hole 的呈現方式。其他 base 保留原本
的呼叫：hole 沒有辦法表達它。

這條規則主要是繞著**優先級**這個陷阱建起來的。`+` 和 `-`、`|`、`^`、`+%`、`-%` 同一個優先級，所以
`"a" + b - c` 解析成 `("a" + b) - c`，那條 `+` 鏈**不是**整段 token——改寫整段會讓運算式重新結合。
因此運算元之間允許出現什麼是一份白名單，而上面那五個只要出現在鏈自己的深度就結束它。

它在以下情況放棄：少於三個運算元；沒有字面值；沒有 hole；鏈跨越一行以上；raw、三引號或帶
`\u{…}` 的字面值；hole 裡帶著 `"`、`\`、`{`、`}`；字面值裡帶大括號——雙寫是正確的但比原本更難讀；
以及 `out = out + …` 這種累積，那裡的 hole 會讓累積器和被內插的值長得一模一樣。

`F406` 會**寫入**一個空行，而做這件事的門檻是刻意訂高的：整棵樹的函式 body 內總共只有**十個**
空行，而 `fmt.zg` 自己 1300 行一個也沒有。所以這條規則只在兩個地方放，而且兩個都是這裡的作者
本來就會放的地方。

**超過一個** guard 組成的一段，後面接一個空行：

```zerg
fn conv_ty(s: str) -> Ty {        fn conv_ty(s: str) -> Ty {
 return TInt if s == "int"         return TInt if s == "int"
 return TStr if s == "str"    →    return TStr if s == "str"
 return TNil
}                                     return TNil
                                  }
```

一個 guard 是它所守護的那一行的一部分；兩個以上是一張**出口表**，而一張表需要邊界——兩邊都要，
所以從函式中途開始的一段，前面也會加一個空行；在 body 的開頭，`{` 本身就是那個邊界。這份克制
就是這條規則的大部分：這棵樹的 218 段 guard 裡有 182 段只有一個 guard，一個都不會被動到。

**三個以上的連續宣告**若從區塊中途開始，前面加一個空行，後面不加：

```zerg
fn c_index(mut &em: Emitter, target: Expr, idx: Expr, sb: Subst) -> str {
 em.used_rt = true

 ct := c_type(c_list_elem(c_infer(em, target)))
 tgt := c_expr(em, target, sb)
 ix := c_expr(em, idx, sb)
```

和 guard 之間的不對稱是結構性的。一段 guard 是**終端的**——後面沒有東西消費它，所以它讀起來像
一張表，兩邊都要邊界。一段宣告是**前言**：這棵樹的 167 段裡有 106 段後面接著 `for`，而那個迴圈
引用了它們宣告的每一個名字；其中 86 段的最後一個宣告，就是下一行 `for` 的迴圈變數。在那裡加空行
會把 `i = 0` 和 `i < n` 拆開。它沒有遠端的邊界，因為它還沒被讀完。

是三個不是兩個——兩個宣告是一對，不是一個段落，這和這條規則說「一個 guard 是它所守護的那一行的
一部分」是同一步。

**自成一行**、而且前後都有程式碼的註解，前面會加一個空行。註解放在那裡是為了帶出一個新的段落
——那正是它自成一行而不是跟在程式碼後面的原因——而這棵樹 body 內既有的空行有一半正是這個形狀。
它適用於任何區塊，所以 `struct` 裡有註解的欄位群，會得到和 Go 一樣的分隔。

它在五種情況放棄：一段 guard 前面的註解，那是這段的**標題**——空行加在註解前面，不加在註解與它
所引介的那張表之間；頂層的註解，那是宣告的註解，宣告之間的間距是作者的；換行引數列表裡的註解，
它屬於它所在的那個元素，加空行反而把它和它在講的東西分開；後面只剩一個 `}` 的註解，它沒有帶出
任何東西；以及那裡已經有一個空行。

它刻意**不做**的是在巢狀區塊的 `}` 之後加空行。那在這棵樹裡是 683 個位置——那不是一條關於可讀性
的規則，而是把整棵樹重寫一遍。

`F407` 把「丟棄接收值」的那個 select arm 的 binder 刪掉：

```zerg
_ := <-cancel => { … }    →    <-cancel => { … }
```

`GRAMMAR` 讓 recv-arm 的 binder 是**可選的**——`<-ch => stmt` 就是完整形式——所以 `_ := <-ch =>` 為
接收到的值取名，只為了說它沒有名字。Go 需要 `_ =`，因為在那裡「未使用的變數」是錯誤；Zerg 沒有這
條規則，所以那個 binder 什麼也沒買到，只讓下一位讀者多問一句「`_` 在哪裡被讀？」。這又是 `F401`
的原則：只要語言為「已經寫下的東西」提供了更短的表面形式，標準形就是短的那個。

它只在有 `=>` 證明「這是一個 select arm」時才動手。**敘述**形式的 `_ := <-ch` 是一個 binding，刪掉
它的 binder 會讓一個裸的 receive 站在原本是敘述的位置上；那個情況是 `L104` 的事，而它只建議、不改寫。

`F408` 是同一個原則的第三次，這次是在 match arm 的 pattern 上：

```zerg
4 | 5 | 6 | 7 => "mid"    →    4..=7 => "mid"
```

`GRAMMAR` 給 arm 一個 **range** 形式，它是 guard `_ if _ in 4..=7` 的糖，所以它說的正是那個
or-pattern 說的事，而且不管有幾個值都只說一次。

**`F409`** 是同一個原則用在 `GRAMMAR` 另一條以展開式定義的糖上:`with e as x { … }` **就是**
`{ x := e; … }`,所以第一個敘述是 binding 的裸 block,就寫成它本來就是的那個 `with`。

```zerg
{                        →   with acquire() as h {
    h := acquire()               use(h)
    use(h)                   }
}
```

觸發條件是**純語法**的——一個裸 block、第一個敘述是 binding。它不得讀那個 binding 的 **`defer`**:`with` 不帶
自己的 teardown,所以一條把 `{ x := e; defer x.close(); … }` 摺進去的規則會把那個 `defer` 刪掉。

兩條都是 **token 規則**,而 `L105` 正是值得把這件事說出來的原因:`with` 在 **parser** 就展開了,所以等到有
AST 的時候,已經沒有 `with` 可以 lint。關於這個形式的每一條規則都因此讀 token,linter 那條也是。

而在這裡，短的那個形式也是**唯一編得過**的那個。pattern 位置上的 `|` 被讀成位元運算子，所以 `1 | 2`
會被折成 `3`、那個 arm 既不中 1 也不中 2——正因如此，編譯器現在直接拒絕 or-pattern，而不是把它 emit 出去。
這條規則做的，是把那個拒絕變回可以編譯的程式碼，而且只針對唯一有可用寫法的那個情況；其他形式的
or-pattern 都等語言層面的工作。

這個順序決定了一個 formatter 可以是什麼：`zerg fmt` 在這裡並沒有改變一個「能跑的程式」的行為——它改寫的
那個程式根本編不過。

它接受的形狀刻意很窄，而每一部分都是承重的：

- 整個 arm **head** 只有整數常值和分隔它們的 `|`，沒有別的。一個 token pass 沒有別的辦法知道某個 `|`
  在 pattern 位置，而 `out <- a | b => …` 是一個 select send arm，它的值剛好含有一個；
- 那些值必須**逐一遞增**——`1 | 3` 不是 `1..=3`，那會把 2 一起收進去；
- 至少兩個分支，而且沒有 guard。

每個邊界保留它自己的 **lexeme**，所以 `0x10 | 0x11` 變成 `0x10..=0x11`，而不是被改寫成十進位。常值的
表面形式是作者的。

### 哪些規則可以關掉

`F1xx`–`F3xx` 沒有商量餘地：它們就是「標準形」的定義，而一個為它們提供選項的格式化器，會變成
兩個人設定成兩種樣子的格式化器。`F4xx` 改的是程式碼的**形狀**而不是它的間距，所以 `--off` 是
為它而存在。`F105` 放在版面而不是改寫，因為它只決定一個既有 token 去哪裡；`F403` 歸在改寫，理由
剛好相反——它會插入沒有人寫過的斷行，也會拿掉併行後的清單不再需要的那個 token；而 `F406` 寫的是
一整行沒有人寫過的東西。

## E1xx–E7xx — 編譯錯誤

這些不是建議。撞上其中任何一條的程式不會建置成功，所以每一條都是**編譯錯誤**、建置會停下來。
它們帶代碼,是因為代碼是一條規則的**穩定身分**,而句子不是:散文會被改得更好,而釘住句子的 gate
會因此變紅。代碼依**回報它的階段**分段,那也是一次建置遇到它們的順序:

| 區段   | 階段 | 回報什麼                                      |
| ------ | ---- | --------------------------------------------- |
| `E1xx` | 詞法 | 不是 Zerg token 的文字                        |
| `E2xx` | 剖析 | 不構成 Zerg 形式的 token                      |
| `E3xx` | 檢查 | 形式成立、但意思兜不攏                        |
| `E4xx` | 產出 | 這個編譯器不會下放的形式,含 `[not yet]`       |
| `E5xx` | 建置 | 程式作為一組檔案,那是單一檔案的文字回答不了的 |
| `E6xx` | 剖析 | 又是剖析器:`E2xx` 滿了,而一段只有一百個號碼   |
| `E7xx` | 產出 | 又是產出器:`E4xx` 滿了,理由一模一樣           |

`E5xx` 是唯一不落在那個順序裡的一段。一次建置在詞法分析被 import 指到的檔案之前就先解析 import,
並在一切都產出之後才去找 `fn main`,所以驅動器自己的發現是把另外四段夾在中間,而不是坐在其中兩段之間。

`E6xx` 根本不是一個階段——它是**接著 `E2xx` 的**,而 `E7xx` 同樣是**接著 `E4xx` 的**,理由一模一樣。
一段只有一百個號碼,剖析器用掉了其中九十八個;當剖析器的拒絕全部搬到同一條回報通道上時,新到的規則在
`E2xx` 裡已經無處可去。產出器晚了一次改動跟上——它的 126 個拒絕裡有 50 個根本沒有代碼,而 `E4xx` 只剩
一個號碼——所以同樣的動作又做了一次。在新的一段接著數下去,才守得住這套機制存在的兩個性質:號碼永不重用,
而讀到號碼的人分得出是哪個階段在說話。

**一段用滿時,就為那個階段開一段接續,並把舊的一段關掉。** 一個階段有兩段開著,就是兩個地方可以配號,
而那正是一週內撞號三次的成因。關掉的做法就是下面已退場表裡 `E299` 在做的事:它從未發出過,而讓一個號碼
退場、卻不花掉它,`E2xx` 讀起來才是**滿的**,而不是還剩一格等人來拿。`E499` 是隔壁一段的同一個動作,
在產出器的號碼越過 `E498` 那天做的:它同樣從未發出過,而 `E4xx` 因此讀起來是滿的。

這也是為什麼上面那張表指名的是**階段**而不是號碼段,以及為什麼 `make error-codes-check` 是按階段回答的:

```text
error-codes-check: next free code per stage — building E513, checking E399, emitting E745,
                                              lexical E112, parser E612
```

號碼段和它們的階段都是從上面那張表讀出來的,而不是在腳本裡另存一份,所以一個階段的答案取自它**最高**
的那一段——接續的意思就是這個。因此新增一段接續的號碼就是在這裡多一列,建議會跟著那一列走。

代碼放在**訊息的最前面**、句子之前:`E109 invalid escape in a rune literal`。當一則診斷帶有位置時,
renderer 的 `error:` 會開在它前面(`error: E109 …`);還沒學會位置的拒絕則單獨印訊息——兩種情況下,
代碼都是那一行的第一個東西。

**代碼在 gate 釘住它時才存在,不會更早。** `scripts/refuse-check.sh` 與 `scripts/reject-check.sh`
都改以代碼而非句子斷言,而一個仍然釘著散文的 `zerg` 案例會具名地失敗——否則一份大部分是代碼、只剩幾句散文的
清單,從外面看起來就像已經做完了。`scripts/error-codes-check.sh` 把三份清單互相拉住:編譯器回報了什麼、哪個 gate 釘住它、

### 已退場的代碼

**退場的號碼永不重用。** 代碼是一個穩定的身分，重用一個號碼會讓舊版建置印出的訊息指向它從未
指過的東西——使用者回報、日誌、去年開的 bug，全都被悄悄改派給另一條規則。所以退場的代碼會離開
上面那張表、改列在這裡，而它所在的區段繼續從自己的最高水位往上數。

`E387`、`E477` 與 `E288`/`E289` 上撞了三次，因為當時唯一的問法是用眼睛掃過整張表。這個答案

這裡的號碼是一個**缺口**，而缺口就是一個別人可能在不知情下重新發出的代碼。

## `zerg lint`

```sh
zerg lint <file.zg>...   # 印出發現；有發現時以非零值結束
```

每一項檢查都只從解析後的檔案回答——沒有型別、沒有流程分析——這讓它對自己能主張什麼保持誠實。
發現依原始碼順序回傳，每一則都帶著它所指的位置（`path:line:col`）。

### 嚴重度,以及它決定的兩個 exit code

一則發現帶有**嚴重度**,共三種:

| 嚴重度      | 印出的樣子              | `zerg lint` | `zerg lint --strict` |
| ----------- | ----------------------- | ----------- | -------------------- |
| **finding** | `path:line:col: L101 …` | **失敗**    | **失敗**             |
| **warning** | `… warning: L601 …`     | 回傳 0      | **失敗**             |
| **info**    | `… info: L106 …`        | 回傳 0      | 回傳 0               |

**finding** 是一條規則在程式上開火,那正是這個工具存在的目的。**warning** 是規則對一個並沒有錯的程式所說的話——
一個會被打包出去的 `#[test]` 是別人有權做的決定——所以它只印出來,不讓工具失敗。**info** 則從不改變任何 exit code。

只有預設的那一種不印形容詞:它就是 `zerg lint` 的本業,不需要在前面加字;而一行**不**改變 exit code 的訊息必須自己
說清楚,否則讀起來就像改變了。

`--strict` 是 `make lint` 跑的那一種,對象是本專案自己的原始碼——在那裡,會被打包出去的測試與永遠不會生效的壓制,
兩者都不可接受。閘門比工具更嚴格在這裡是有前例的:`refuse-check` 對一次拒絕所斷言的,就多於 `zerg build` 的要求。

### 壓下一則發現——`#[allow(…)]`

statement 上的 `#[allow(L103)]` 會在它所領的 statement 範圍內壓下該代碼;若該 statement 帶一個區塊,區塊也算在內——
範圍就是那個 statement 的大小,這是**一條**規則,而不是在「一行」與「一個 scope」之間二選一。它不會延伸到下一個
statement,也到不了另一個檔案;刻意**沒有檔案層級的範圍**。它只收 **`L` 代碼**:`E` 代碼是編譯器診斷,壓下一個等於
把繞過編譯器檢查變成官方功能。見 [Decorator](../core/decorators.zh-TW.md)。

有兩個代碼講的是「壓制」本身。`L106` 比它看起來重要:過期的 allow 壓住了一條早已不再開火的規則,
而真正的問題回來時沒有人會知道。

| 代碼   | 嚴重度      | 發現                                             |
| ------ | ----------- | ------------------------------------------------ |
| `L106` | **info**    | 這個 allow 沒有東西可壓                          |
| `L107` | **warning** | 這個 allow 指名了沒有規則對應的代碼,永遠不會生效 |

### L1xx — 死碼

| 代碼   | 發現                          | 為什麼值得印一行                                                         |
| ------ | ----------------------------- | ------------------------------------------------------------------------ |
| `L101` | 未使用的 import               | 該模組被讀取、解析、併入程式卻毫無用處，還對下一位讀者謊報這個檔案的依賴 |
| `L102` | 從未被呼叫的私有函式          | 公開的是模組的介面；私有而無呼叫者的，就只是死碼                         |
| `L103` | 從未被讀取的 binding          | 那個值是為了沒有人而計算的                                               |

| `L105` | `with … as x` 而 `x` 從未被讀 | block 本來就把資源綁進這段區間;那個名字是沒有人說出口的部分              |

```text

L102 private function `never` is never called
L103 binding `unused` in `main` is never read

```

`L102` 永遠不會報 `main`：不管原始碼怎麼說，runtime 都會呼叫它。

`L104` 就是 `L103` 對 `_` 閉口不談的原因：沒有人讀 `_` 正是 `_` 的**意思**，所以「從未被讀取」是唯一
不值得對它說的事。同一件冗餘的 select arm 寫法是 `F407` 的事，因為 `GRAMMAR` 讓那個 binder 是可選的，
刪掉它之後剩下的仍然是一個 arm；敘述形式的 binder 沒有這種寫法。

### L2xx——null safety

這裡沒有一條是編譯錯誤：每一支程式都跑得動，只是做的事跟它寫的略有出入。這正是它們屬於 linter
而不是編譯器的原因。

| Code   | 發現                       | 為什麼值得報一行                                       |
| ------ | -------------------------- | ------------------------------------------------------ |
| `L201` | `?? nil`                   | fallback 本身就是缺席值，所以這個 `??` 什麼都沒改      |
| `L202` | 回傳 `T?` 的函式裡用了 `!` | `?` 會把缺席交回去；`!` 則把它變成 abort，而且比較好打 |

```text
L201 `?? nil` in `keep` changes nothing — the result is optional either way
L202 `!` in `forced`, which answers a `T?` — `?` hands the absence back instead of aborting
```

兩條都只從解析後的檔案回答，跟這裡其他規則一樣——`?? nil` 是一個**形狀**，「回傳 `T?` 的函式裡的
`!`」也是。兩者都不需要任何沒被寫下來的型別。

### L3xx — 捕獲

| 代碼   | 規則                                                       |
| ------ | ---------------------------------------------------------- |
| `L301` | 被 `spawn` / `defer` 捕獲、且在捕獲之後被寫入的 `mut` 綁定 |

`spawn f(k)` 與 `defer f(k)` 把引數取為**快照**，在它們被寫下的那一行。之後對 `k` 的寫入
不會被那個呼叫看到 —— coroutine 可能還沒開始，延後的呼叫也還沒執行：

```zerg
mut k := 5
spawn show(k)      # 捕獲 5
k = 99
# coroutine 印出 5
```

那是正確的語意，也是這個語言裡最容易被誤讀的一件事。它是 **lint** 而不是 error，因為程式是對的、
而且快照通常正是想要的 —— 工具說出發生了什麼，而不是拒絕它。

**channel 也會被報，而且只在「重新綁定」時**。channel 是類似 `Ref` 的 **handle** 而不是值：
coroutine 拿到的是同一條 channel 的另一個 handle，之後送出的東西**看得到** —— 但送出是 `ch <- v`，
那不是寫入，本來就不會被報。真正會走到這條規則的是 `ch = <另一條 channel>`，之後 coroutine 握著的是
**舊的**那條。早先的版本把 channel 整個排除，結果只壓掉了正確的回報。

**寫入不只是賦值**：捕獲 `xs` 之後的 `xs.append(2)` 正是這條規則存在的理由 —— 被捕獲的 `list`
是以深拷貝拍下的快照。但也**不是每個呼叫**：捕獲之後的 `show(k)` 是讀取。一個呼叫要算寫入，得是把
該綁定傳進 `mut &` 參數；一個 method 要算寫入，得是會透過 receiver 寫回去的那些。兩者都從宣告讀出來，
而不是在這裡猜。

它只看同一個 block 內、捕獲之後的語句 —— 包含 closure 或 `guard` 帶著的那個 block，那種 block 掛在
運算式上而不是語句上。來自**另一個** block 的寫入不報：這條規則報的是**會誤導的形狀**，不是所有可能
的形狀。

指名（見[文法](../surface/grammar.zh-TW.md)）,所以 `Red` 單獨一個在哪一個 enum 裡都是
_E383 `Red` is a variant of `Colour`, and a variant is named through its enum_;而帶限定的 `Signal.Red` 是
**在它指名的那個 enum 裡面**解析的,兩份宣告因此是兩個不同的 variant、不會相爭。這條規則是從 linter 裡拿掉,
而不是留著繼續跑——否則它在 `lint-check` 裡那個案例就會一直斷言下去。

`mut fn` 不是提示:它讓 receiver 變成 `mut &`,所以**每一個**呼叫端都得把實例放在 `mut` 綁定裡。一個只讀的
method 讓呼叫端付這個代價卻什麼也沒回報 —— 而他們看不出原因,因為簽章就是全部的契約,而 `mut fn` 就是它說的
全部。判準是對 `this` 的**寫入**,不是提到它。

### `L5xx` —— 轉換

| 代碼   | 規則                                 |
| ------ | ------------------------------------ |
| `L502` | 一個**字面值**取了不屬於它自己的型別 |

偏離字面值預設的採用是一則 finding（[型別](../core/types.zh-TW.md#into--一個普通的轉換-spec)）——所以
`1.5 + 1` 會被報出來,`1.5 + 1.0` 不會。它是建議性的:採用是合法的,而頁面應該把它顯示出來——`1` 與 `1.0`
對**讀者**來說就該是不同的型別,不是只對編譯器而言。

`L501` 曾與它並列,現已**退役**。它報的是一個值在 position 上被轉換了——`f: float = i`——那曾是合法的、
一步的、而且看不見的。position 只會包值、絕不轉換值（[型別系統](../core/type-system.zh-TW.md)）,所以它的
整個主題如今是一個拒絕;而一條「它要報的程式編譯器都不收」的 lint,對任何給它的程式都報不出東西。這個編號
不會被重用:在舊 log 裡遇到 `L501` 的讀者,應該找得到它是什麼、以及它為什麼走了。

這一條是 linter 唯一無法從剖析樹回答的規則。字面值採用了什麼型別是關於**型別**的事實，所以由 lowering walk
記錄下來、`zerg lint` 去問那個 walk——它產生的 C 會被丟掉。編譯不過的程式一則也不會報，這是對的：一個型別
本身就錯的程式，沒有什麼型別上的建議好給。

### `L6xx` —— binary 帶著什麼

| 代碼   | 規則                                                       |
| ------ | ---------------------------------------------------------- |
| `L601` | `*_test.zg` 之外的 `#[test]` 或 `#[fixture]` — **warning** |
| `L602` | `*_test.zg` 之外的 `assert` — **warning**                  |

這樣的函式是**合法**的,而且會**被打包出去**:它和其他函式一樣被編進 binary,在生成的 C 裡出現兩次,沒有任何東西
呼叫它,而它的 `import "testing"` 也跟著一起走——一個只給測試用的依賴就是這樣進到出貨的程式裡的。所以訊息說的是那個
**後果**,而不是偏好。只說「把它搬走」的警告是風格建議,讀者學會略過;讀者真正要權衡的是產物裡的死碼。

`#[allow(L601)]` 可以為一個刻意要打包出去的 `#[test]` 消音。一個項目一個 decorator,所以兩者寫成一個:
`#[allow(L601), test]`。

`L602` 是同一套論證,只是對象從死碼換成一條**活著的**主張。`assert` 永遠會被編譯進去——沒有任何旗標能拿掉它,
這是刻意的:帶著斷言的程式和拿掉斷言的程式是兩個程式,而沒有人會把要緊的東西寫進一條可能不會跑的檢查裡。所以
測試檔以外的 `assert` 是一條會出貨、而且能讓執行中的程式 abort 的檢查;訊息點名**替代寫法**,這才讓這條警告
站得住腳:產品程式碼裡的 `assert` 不是比你本來要寫的檢查**更弱**,而是**更不具體**——它只說主張不成立,從不說
它本來要說什麼。`raise ValueError("xs must be non-empty") if xs.len() == 0` 兩件事都說了。

`#[allow(L602)]` 可以消音:放在 `fn` 上涵蓋整個函式本體,放在單一敘述上就只涵蓋那一條。之後把程式碼搬進
`*_test.zg`,`L106` 會叫你把這個 allow 刪掉——這正是讓消音不會活得比它的理由更久的機制。

## 新增一條規則

一個新的**表面形式**必須在同一次變更裡附上 `test-data/fmt/` 的案例，而不只是一條規則。formatter 的
失敗是穩定的——印錯的形式第二次還是印成同樣的錯——所以在真的有案例含到那個形狀之前，
`make fmt-corpus` 一直是綠的。目前找到的兩個間距缺陷（`chan[T]<-` 那一族，以及 `-1`）都藏在沒有任何
案例含到的形式裡。

依它的**效果**所屬的分組取下一個號碼，加進
[`src/compiler/zerg/fmt.zg`](../../src/compiler/zerg/fmt.zg) 或
[`lint.zg`](../../src/compiler/zerg/lint.zg) 的表，然後加到這裡。會移動程式碼的規則屬於 `F4xx`，
而且應該可以開關；只做間距或縮排的，不需要。
