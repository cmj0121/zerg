# Zerg 編譯診斷

編譯器回報的每一個代碼,以及它指名的規則。屬於
[語言參考](../language.zh-TW.md)的一部分。亦有 [English](diagnostics.md)。

`F` 與 `L` 代碼是**工具**對一個「已經建置得起來」的程式所說的話,由[格式化器](fmt.zh-TW.md)與
[檢查器](lint.zh-TW.md)各自帶著。

這些不是建議。撞上其中任何一條的程式不會建置成功，所以每一條都是**編譯錯誤**、建置會停下來。
它們帶代碼,是因為代碼是一條規則的**穩定身分**,而句子不是:散文會被改得更好,而釘住句子的 gate
會因此變紅。代碼依**回報它的階段**分段,那也是一次建置遇到它們的順序:

| 區段    | 由誰回報 | 回報什麼                                      |
| ------- | -------- | --------------------------------------------- |
| `E1xxx` | 詞法     | 不是 Zerg token 的文字                        |
| `E2xxx` | 剖析     | 不構成 Zerg 形式的 token                      |
| `E3xxx` | 檢查     | 形式成立、但意思兜不攏                        |
| `E4xxx` | 產出     | 這個編譯器不會下放的形式                      |
| `E5xxx` | 建置     | 程式作為一組檔案,那是單一檔案的文字回答不了的 |
| `E9xxx` | 未建置   | 語言有、而這個編譯器還沒建起來的形式          |

`E5xxx` 是唯一不落在那個順序裡的一段。一次建置在詞法分析被 import 指到的檔案之前就先解析 import,
並在一切都產出之後才去找 `fn main`,所以驅動器自己的發現是把另外四段夾在中間,而不是坐在其中兩段之間。

`E9xxx` 根本不是一個階段,而且它是唯一一段、其中的代碼講的不是眼前這支程式。`[not yet]` 說的是**語言**
有這個形式、而這個編譯器還沒把它建起來——那和上面每一列都是不同種類的句子,也是不同種類的一生:它在形式
被建好時退場,而不是在某條規則改變主意時退場。這樣的代碼有 104 個原本坐在各階段的號碼段裡,一個代碼就是
未來的一個洞。給它們自己的一段,那份翻動就被關在裡面,而五個階段的號碼段維持緊密。

**一段有一千個號碼,而一個階段剛好擁有一段。** 從前不是這樣:編號是三位數、一段只有一百個號碼,剖析器
用掉其中九十八個之後接到 `E6xx`,產出器同樣接到 `E7xx`,於是第一位數字不再指出階段——而那正是讀者無法
自己推出來的唯一一件事。四位數把整個想法一起退掉。沒有接續號碼段、沒有開一段接續的規則,也沒有讀者需要
去記哪兩段其實是同一段。萬一哪天真的用滿了,就為那個階段開一段接續、並把舊的一段關掉——一個階段有兩段
開著,就是兩個地方可以配號,而那正是一週內撞號三次的成因。

**三位數的那套編號是整批退場的**,在一次提交裡,發生在 Zerg 還沒有任何發行之前。四位數的代碼不會重複到
任何一個三位數的代碼,因為它們是不同的字串,所以舊版本印出來的訊息仍然是它當初的意思——而那就是「號碼
退場」保護的全部。新舊對照留在那次提交裡,不放在這裡:一份目錄講的是代碼**現在是什麼**,再擺一張它們
曾經是什麼的表,只會是一份永遠讀不完的清單。

`make error-codes-check` 會按號碼段回答下一個可用的代碼是什麼:

```text
error-codes-check: next free code per range — lexical E1012, parser E2065, checking E3095,
                                              emitting E4074, building E5012, unbuilt E9105
```

號碼段是從上面那張表讀出來的,而不是在腳本裡另存一份,所以新增一段就是在這裡多一列,除此之外什麼都不必動。

代碼放在**訊息的最前面**、句子之前:`E1009 invalid escape in a rune literal`。當一則診斷帶有位置時,
renderer 的 `error:` 會開在它前面(`error: E1009 …`);還沒學會位置的拒絕則單獨印訊息——兩種情況下,
代碼都是那一行的第一個東西。

**代碼只在編譯器裡宣告一次。** `src/compiler/zerg/rule.zg` 就是那份登錄表:`pub enum Rule` 裡一條規則
一個 variant、各自帶著自己的號碼,而每一條回報管道收的都是 `Rule` 而不是字串。於是手寫的代碼是型別錯誤、
沒有身分的規則根本寫不出來,而整套重新編號也只是改那一個檔案。它同時是兩份平行修改相遇的地方:新代碼就是
那裡的一行,第二個人的那行會落在同樣的位置,於是 **git** 會先講話,不必等 CI 問。

**代碼在 gate 釘住它時才存在,不會更早。** `scripts/refuse-check.sh` 與 `scripts/reject-check.sh`
都改以代碼而非句子斷言,而一個仍然釘著散文的 `zerg` 案例會具名地失敗——否則一份大部分是代碼、只剩幾句散文的
清單,從外面看起來就像已經做完了。`scripts/error-codes-check.sh` 把四份清單互相拉住:登錄表宣告了什麼、
哪個站點回報它、哪個 gate 釘住它、以及這張表列了什麼。問它這個問題,問出了**十三條從來沒有任何案例讓它發火的規則**;
它們就放在 `reject-check.sh` 的最後一節。

一個 reject 案例只有在數個案例共用同一個代碼時才另外留下**句子**,因為那時每個案例證明的是規則指名了哪些值。
seed 全程維持句子比對:代碼是語言的契約,而 seed 是建置正式編譯器的工具、不是它的一部分
(這條線[一致性](../conformance.zh-TW.md)在拒絕標記 seed 的缺口時就畫過)。

編譯成功、程式回答 0。它說**緊接著**，是因為第一位數字屬於前綴自己的產生式：`0x_1F` 在 `0x`
後面確實有數字，卻仍然不是一個數——分組用的 `_` 位在兩位數字之間，而它左邊一位也沒有。

其中曾有一條規則，現已**退場**。它報告的是 pattern 位置上的裸名字——「`Zzz` 是某個 enum 的
variant，而 pattern 要透過 enum 指名」——判準卻是名字的第一個字母，而那個 parser 什麼都還沒
解析、也不知道有哪些 enum。於是它會對一個根本沒宣告 enum 的程式開火，句子裡指名的那個 enum
並不存在。pattern 位置上的裸名字**永遠**是一個新的 binding（[Grammar](../surface/grammar.zh-TW.md)），
不看大小寫；而這條規則原本想擋的錯——兩個 variant 沒帶 enum 寫出來——改由 `E4032` 回答：第一個
arm 綁住了全部，它下面的 arm 都到不了。

### 已退場的代碼

**退場的號碼永不重用。** 代碼是一個穩定的身分，重用一個號碼會讓舊版建置印出的訊息指向它從未
指過的東西——使用者回報、日誌、去年開的 bug，全都被悄悄改派給另一條規則。所以退場的代碼會離開
上面那張表、改列在這裡，而它所在的區段繼續從自己的最高水位往上數。

這也是這份目錄可以**被查詢**的原因。`make error-codes-check` 會報出**每個區段的下一個可用
代碼**，那正是任何要新增規則的人手上的問題——包括兩個平行工作的 agent，牠們一週之內就在三個
號碼上撞了三次，因為當時唯一的問法是用眼睛掃過整張表。這個答案
只在水位以下每個號碼都有交代時才靠得住，所以閘門就是這樣要求每個區段的：既不在上表、也不在
這裡的號碼是一個**缺口**，而缺口就是一個別人可能在不知情下重新發出的代碼。

**目前一個都沒有。** 這套編號之前的那一套是整批退場、而不是一次退一個，而在那之後也還沒有任何
代碼退場過——每個號碼段水位以下的號碼，都在上面那份目錄裡。第一個退場的代碼會列在這裡，連同它
離開的理由。
